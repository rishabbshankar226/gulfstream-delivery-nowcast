| Hazard | Answer | Evidence |
|---|---|---|
| A lock written after the release time | Absent for the configured date. Present if the date in `config/calendar.json` is wrong (F018) | `live.py:253-260` `before_release` and `wall_clock_ok` use the release date typed into the calendar. `live.py:357` refuses a prediction when `now` is on or past that date, or (real runs) within 10 minutes of 00:00 ET. `live.py:383` checks the real clock again before `release_create` at `:387`. `live.py:396` only warns when `published_at` is on or after the configured date. | A lock whose hash does not match its release | Present before the codex merge (fixed by `163eac0`) | `live.py:281-289` `write_lock_json` records `sha256(body)` of the local prediction file and the tag's commit, and never reads the file at the tag or the release notes. Commit `163eac0` adds the comparison with the tagged file. For 2026Q3 the three hashes agree (`LOCK_CHECK.md` rows 1 to 4) |
| A score read from the wrong exhibit or the wrong quarter | Absent | `sec.py:122-129` `results_8k` takes the first 8-K with item 2.02 filed after the quarter's fiscal end and within 70 days. The previous quarter's release is filed before this quarter ends, and the next quarter's falls outside 70 days. `sec.py:115-119` picks the Exhibit 99.1 file by name. `sec.py:179-207` reads the first numeric column of the "Gulfstream Aircraft Deliveries (units)" table and raises when large plus mid does not equal the total (`:198-199`) or when the release's own delivery sentence disagrees (`:205-206`). | A second lock in one quarter | Absent | `live.py:338` returns when `<Q>_lock.json` exists. `live.py:350-356` stops when the release exists. `live.py:387-391`: `gh release create` fails on an existing tag, and the run then records the existing release. `live.py:366-368`: a prediction file already tracked is never rewritten |
| A missed-lock path that still prints a lock | Absent | `live.py:340-345`: past the release date with no lock, the run logs "missed its lock window ... no late lock" and returns. `report.py:172-173` prints "no lock (the quarter missed its window)" for a scored quarter without a lock; `site/app.js:135` and `:147` do the same. `tests/test_after_score.py` covers the README, post and note for that state |
| A lock computed from a registry copy that does not cover the quarter | Present (F017) | `live.py:370-375`: the lock reads `newest_stored(root)`, the newest snapshot with a stored subset, and checks only that it is dated before the release date. Full subsets are stored only in the seven days before a release (`live.py:206-210`). If every download in that window fails, the newest stored subset is the previous quarter's (today: 2026-10-29), which ends weeks before the new quarter does. The lock would then publish a partial count as the quarter's estimate. The preregistration records that the FAA refused a GitHub runner "on eight straight weeks to 2026-10-18" |
| Date and timezone edges: DST end on 2026-11-01, a late-January release | Absent | `live.py:18` uses `zoneinfo` `America/New_York`; `lock_due` (`:244-250`), `before_release` (`:253-254`) and `wall_clock_ok` (`:257-260`) convert with it, so the eve and midnight are right in EST and EDT. `wall_clock_ok` builds midnight with `replace(tzinfo=ET)`, which is correct for `zoneinfo`. Snapshot dates are America/Chicago dates (`faa.py:40-41`); between 00:00 and 01:00 ET the Chicago date is still the day before, so a run in that hour on the eve finds no snapshot dated the eve and does not lock early, and a run in that hour on the release date is refused by `before_release` |
| The workflow's clock | A lock can be missed, never made late | `.github/workflows/nowcast.yml` cron `17 0,12 * * *` (UTC). Since 2026-11-01 the first run's commits land between 06:00 and 07:21 UTC, about six hours late. On the eve that is 01:00 to 02:21 ET, when a snapshot dated the eve exists, so the lock is due (2026Q3 locked this way at 01:51 ET). If the eve's downloads fail, the only path left is `t.hour >= 19` ET on the eve, which needs the 00:17 UTC run to start on time; with a six-hour delay it starts after midnight ET and `before_release` refuses it. The quarter then has no lock, and every surface says so |
| The calendar is typed by hand | Operational, disclosed in `GO_PUBLIC.md` | `live.py:326-329`: no release date for the live quarter means "nothing to lock". `config/calendar.json` holds only `2026Q3`. `fiscal.py:57`: a first quarter's fiscal end must be added under `fiscal_ends`. So no 2026Q4 lock can happen until the owner adds GD's release date (lead L15) |

Also read: `daily.py:76-169`. Every `except` there prints the error and sets a non-zero exit (`:127-129`, `:139-141`, `:145-147`, `:158-160`), except `:116-117`, which prints "git pull failed" and carries on; a later push then fails loudly at `:163-168`. `gitops.py:89-100` `refuse_markers` reads the working file and only some suffixes; commit `44b3715` reads the staged blob instead.
